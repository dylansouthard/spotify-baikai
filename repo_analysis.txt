Technical handoff: adding MCP to spotify-baikai
Executive summary
The repository is a small ESM Node/Express application. Its REST interface currently accepts a Spotify access token directly in Authorization: Bearer …, forwards that token to Spotify, and returns simplified Spotify responses.
The migration should add MCP beside REST, not replace it:
Existing REST caller                         MCP client
(Spotify bearer token)                       (Baikai bearer token)
          |                                           |
          v                                           v
   Express controllers                      /mcp + MCP auth
          |                                           |
          +-------------------+-----------------------+
                              |
                              v
                     shared Spotify services
                              |
                              v
                       Spotify Web API
The most reusable component today is playback: services/spotifyPlayback.js already contains the direct-play, verification, reusable private-playlist fallback, locking, diagnostics, and detailed result behavior.
Taste-profile orchestration is reusable in concept, but most of it is currently private inside an Express controller and must be extracted before MCP calls it.
Current OAuth is not an MCP authorization server. It effectively proxies Spotify’s OAuth endpoints so ChatGPT Actions receives Spotify tokens directly. Standards-compliant MCP requires a separate Baikai access token that identifies the MCP user; Spotify credentials should remain server-side.
No files were edited or packages installed. The existing 35 tests pass under Node v22.21.1 when local test servers are allowed to bind to loopback. The worktree already contained an untracked controllers/authController.test.js; preserve it.
Documentation checkpoint, as of 2026-09-23:
The current MCP TypeScript SDK uses split packages such as @modelcontextprotocol/server and framework/runtime adapters. Its Express recipe uses a stateless handler mounted at /mcp. Official MCP TypeScript package guide, Express serving guide.
MCP 2026-07-28 has a stateless protocol core and prefers Client ID Metadata Documents; DCR remains for compatibility but is deprecated in the current MCP specification. MCP 2026-07-28 release.
Current OpenAI guidance requires OAuth 2.1/MCP discovery, PKCE S256, resource/audience binding, token validation, and current ChatGPT-specific linking metadata. OpenAI MCP authentication guidåe.
These requirements and SDK package names must be rechecked at Milestones 1 and 6 because MCP and client support are evolving quickly.

3. Existing request/auth flow
Normal authenticated Spotify REST request
There is no Baikai user authentication in this path.
REST caller
  |
  | Authorization: Bearer <Spotify access token>
  v
Express route
  |
  v
Controller
  |
  | getBearerToken(req)
  | -> { Authorization: "Bearer <same token>" }
  v
Axios
  |
  v
Spotify Web API
Important properties:
Baikai does not validate the bearer token locally.
Baikai does not identify or persist a user.
Baikai does not refresh the token automatically.
A missing token becomes an empty Bearer header and fails at Spotify.
Controllers generally convert Spotify errors through the existing REST error format.
The REST flow should remain available during MCP development.
/taste-profile
GET /taste-profile
  |
  | Spotify bearer token
  v
getUserTasteProfile
  |
  +--> 3 x /me/top/tracks
  |      long_term, short_term, medium_term
  |
  +--> 3 x /me/top/artists
  |
  +--> /me/albums?limit=10
  |      |
  |      +--> sampled historical album-page requests
  |
  +--> paginated /me/following?type=artist
  |      up to 300 fetched, up to 100 sampled
  |
  v
Combined JSON with partial errors
The four top-level categories are awaited sequentially. Requests inside a time-range set or album phase are parallelized.
Behavior to preserve:
Three time ranges for artists and tracks.
Track titles grouped by the first credited artist.
Recent saved albums.
Random historical saved-album phases.
Followed-artist sampling.
Partial results instead of rejecting the whole request when one Spotify subsection fails.
Existing quirks that need characterization tests before extraction:
Top-item error arrays are spread into an object; numeric keys from artist errors can overwrite numeric keys from track errors.
sampleItems() returns a different shape in the “all remaining items fit” branch than getSavedAlbums() expects.
Saved-album JSON uses saved_at, while the OpenAPI schema describes saved.
The implementation emits total, most_recent, and phase_* entries; OpenAPI describes a different sampled_albums shape.
Followed-artist and saved-album sampling is intentionally nondeterministic.
There are currently no taste-profile tests.
Do not silently correct these while extracting the service. First record current intended and accidental behavior with fixtures; fix schema/behavior separately if desired.
Playback
PUT /player/play-tracks
  |
  +--> validate URI array / device / details
  +--> GET /me to identify Spotify account
  +--> acquire per-account filesystem lock
  +--> PUT /me/player/play with raw uris
  +--> poll GET /me/player at delays 0/300/600 ms
  |
  +--> verified? ---- yes ---> structured success or HTTP 204
  |
  no
  |
  +--> find/reuse/create reserved private buffer playlist
  +--> replace then append playlist items in ordered chunks of 100
  +--> play playlist context
  +--> verify track + context + optional device
  +--> structured outcome or detailed failure
Key details:
Direct-track playback is verified against actual player state.
Relinked track IDs are recognized.
Explicit device IDs are checked during verification.
Context playback reports command acceptance but is not verified.
The fallback playlist is private and reusable.
The saved playlist ID and lock live in .spotify-playback/ by default.
Concurrent playback for the same Spotify user is rejected with PLAYBACK_BUSY.
Device diagnostics are attached to certain failures.
runPlayback() returns detailed structured failures instead of throwing most playback errors.
The default REST success remains an empty 204; details=true returns JSON.
MCP should call runPlayback() directly and always return the detailed structured result. It should never call the REST endpoint or reproduce the fallback algorithm.
Regular Spotify OAuth
Browser -> GET /login
Baikai -> Spotify /authorize
           redirect_uri = REDIRECT_URI
Spotify -> GET /callback?code=...
Baikai -> Spotify /api/token
Baikai -> browser JSON {access_token, refresh_token}
Weaknesses relevant to planning:
/login does not create a state value.
/callback does not validate state.
Tokens are returned to the caller and not stored.
/refresh-token accepts a supplied refresh token and returns only a new access token.
If Spotify returns a rotated refresh token through /refresh-token, the handler currently discards it.
Legacy ChatGPT Action OAuth
ChatGPT Action
  |
  | GET /login-openai?state=...
  v
Baikai
  |
  | redirects directly to Spotify
  | Spotify redirect_uri = ChatGPT's configured callback
  v
Spotify authorization
  |
  | code + state
  v
ChatGPT callback
  |
  | POST /token-openai
  | code, redirect_uri, grant_type
  v
Baikai
  |
  | POST Spotify /api/token
  | using SPOTIFY_ID + SPOTIFY_SECRET
  v
Spotify token response
  |
  v
Baikai returns Spotify access/refresh tokens to ChatGPT
This is an OAuth proxy for the old Action contract. The bearer token later sent to REST is a Spotify token, not a Baikai-issued credential.
/token-openai supports both authorization-code and refresh grants and preserves a rotated Spotify refresh token if one is returned. It does not act as a standards-compliant authorization server:
No Baikai user identity is established.
No Baikai token is minted.
Incoming Action client_id and client_secret are observed for diagnostics but not validated.
The supplied redirect_uri is forwarded to Spotify.
There is no PKCE validation.
There is no resource/audience binding.
There is no protected-resource or authorization-server metadata.
There is no token revocation, introspection, or Baikai scope enforcement.

Before exposing playback through MCP:
Move playback input parsing/validation into a pure helper.
Move Spotify-response redaction into a reusable helper.
Move getDevices Axios work into a service.
Do not move or rewrite the runPlayback() algorithm.
5.4 Extract Spotify OAuth primitives
Add services/spotifyOAuthService.js containing transport-independent functions:
Build Spotify authorize URL.
Exchange an authorization code.
Refresh an access token.
Normalize token responses.
Fetch /me after connection to obtain stable Spotify account identity.
Legacy controllers should call these functions while keeping their existing HTTP behavior.
5.5 Keep error models separate from transports
Shared services should either return a documented result or throw a transport-neutral error. They should not call throwError(..., res).
REST maps the error to its current JSON response. MCP maps it to a sanitized isError tool result. Authentication failures remain HTTP 401, not ordinary Spotify tool errors.

Design rules:
Construct MCP auth context from verified credentials, never tool arguments.
Keep tools thin.
Return both concise text content and structured content where supported.
Define strict input and output schemas.

Keep MCP transport stateless. Durable account state belongs in SQLite.
7. Database proposal
Library recommendation
Use better-sqlite3 unless the deployment environment cannot build or run its native module.
Why it fits this repository:
Small API.
Prepared statements and transactions are straightforward.
Credential lookups are tiny and fast.
No ORM is needed.
The application already uses synchronous configuration/bootstrap patterns.
Do not keep a transaction open while awaiting a Spotify HTTP request; the library explicitly warns against async work inside its transaction wrapper. better-sqlite3 API.
If the deployment is pinned to a Node version with a production-approved node:sqlite API, the coach can reevaluate. The repository currently has no Node engine declaration, so relying on a particular built-in SQLite API prematurely would be risky.
File location
Recommended:
BAIKAI_DB_PATH=/persistent/path/spotify-baikai.sqlite
Development fallback:
data/spotify-baikai.sqlite
Add database files, -wal, and -shm companions to .gitignore. The production path must be on a durable local filesystem, not an ephemeral deployment layer or an unreliable network share.
Migration strategy
Use small numbered SQL files and a schema_migrations table:
db/migrations/001_initial.sql
db/migrations/002_oauth_transactions.sql
Run migrations once during startup before listen(). Fail startup if migration or encryption-key validation fails.
Recommended pragmas:
foreign_keys = ON
journal_mode = WAL
A bounded busy_timeout
Back up the database and its WAL correctly.
Core schema
Use at least two durable tables. One table would incorrectly combine Baikai identity and Spotify connection lifecycles.
CREATE TABLE app_users (
  id TEXT PRIMARY KEY,
  auth_issuer TEXT NOT NULL,
  auth_subject TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE (auth_issuer, auth_subject)
);

CREATE TABLE spotify_connections (
  user_id TEXT PRIMARY KEY
    REFERENCES app_users(id) ON DELETE CASCADE,

  spotify_user_id TEXT NOT NULL UNIQUE,

  refresh_token_enc TEXT NOT NULL,
  access_token_enc TEXT,
  access_token_expires_at INTEGER,

  scopes_json TEXT NOT NULL,
  encryption_key_id TEXT NOT NULL,
  token_version INTEGER NOT NULL DEFAULT 0,

  reauth_required_at INTEGER,
  disconnected_at INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
*_enc should be a versioned authenticated-encryption envelope containing nonce, ciphertext, and authentication tag. Do not use reversible obfuscation or a hash for refresh tokens; they must be recoverable for Spotify refresh.
A third short-lived table is sensible for Spotify linking:
CREATE TABLE spotify_oauth_states (
  state_hash TEXT PRIMARY KEY,
  user_id TEXT,
  authorization_request_id TEXT,
  expires_at INTEGER NOT NULL,
  consumed_at INTEGER,
  created_at INTEGER NOT NULL,
  FOREIGN KEY (user_id) REFERENCES app_users(id)
);
Store only a hash of the browser-visible state value. Consume it once.
Why this is the smallest sensible split
app_users survives Spotify disconnects.
spotify_connections can be replaced or deleted without deleting the Baikai identity.
OAuth state has a short lifecycle and should not be mixed with credentials.
One Spotify connection per internal user is adequate initially.
Multiple Spotify accounts per user can be introduced later by adding a connection ID and selection semantics; do not prebuild that now.
Optional authorization-server tables
Do not add these until the Milestone 6 provider decision.
If Baikai hosts its own OAuth authorization server, it will probably also need:
Pending MCP authorization requests.
One-time authorization codes.
Hashed MCP refresh tokens.
Hashed opaque MCP access tokens, or JWT signing-key metadata and revocation state.
Registered clients if DCR is supported.
CIMD clients do not necessarily require a durable client row, though safely cached/validated metadata may be useful.

New authorization layer
The MCP relationship must issue or accept a Baikai credential:
MCP client
    |
    | Baikai access token:
    | subject = Baikai user
    | audience/resource = Baikai MCP server
    | scopes = Baikai tool permissions
    v
spotify-baikai
    |
    | stored Spotify access token:
    | subject = Spotify account
    | scopes = Spotify API permissions
    v
Spotify
A likely nested authorization flow is:
1. MCP client discovers Baikai protected-resource metadata.
2. Client identifies/registers itself with Baikai's authorization server.
3. Client starts authorization code + PKCE against Baikai.
4. Baikai starts a separate Spotify authorization flow.
5. Spotify redirects back to a Baikai callback, not the MCP client.
6. Baikai exchanges the Spotify code and stores encrypted Spotify credentials.
7. Baikai creates/identifies the internal user.
8. Baikai returns a one-time Baikai authorization code to the MCP client.
9. Client exchanges that code with PKCE at Baikai's token endpoint.
10. Baikai issues its own MCP access/refresh tokens.
11. Subsequent `/mcp` calls carry only the Baikai token.
This preserves the two authorization relationships even if the browser experience chains them together.
Spotify credential behavior
The credential manager should:
Load the user’s Spotify connection.
Return the cached encrypted access token if it remains usable beyond a safety window.
Otherwise refresh with Spotify.
If Spotify returns a new refresh token, atomically replace the old one.
If no refresh token is returned, retain the previous one.
Update access token, expiry, scope, and version together.
On invalid_grant, mark reauthorization required and stop retrying.
Never return Spotify credentials to the MCP client.
Survive process restart using only DB state and the external encryption key.
Spotify’s current documentation says refresh responses may or may not rotate the refresh token; the old token must be retained when no replacement is returned. It also currently documents a finite refresh-token lifetime, so reauthorization must be an expected state rather than an exceptional mystery. Spotify refresh documentation.
Encryption
Recommended envelope encryption:
AES-256-GCM using Node’s crypto module.
Random 12-byte nonce per encryption.
Authentication tag stored with the ciphertext.
Associated data binding the token to its user/connection and token type.
Key supplied outside SQLite, such as SPOTIFY_TOKEN_ENCRYPTION_KEY_BASE64.
encryption_key_id stored with each record.
Fail startup if the configured key is missing or malformed.
Retain old keys temporarily during planned key rotation.
Never log plaintext, ciphertext envelopes, or keys.
Encrypt cached access tokens too. They are shorter-lived than refresh tokens but are still credentials.
Refresh concurrency
Do not hold a SQLite transaction open across the network request.
Use either:
A short DB-backed refresh lease plus an optimistic token_version, or
An explicitly documented single-process assumption with optimistic versioning.
The first approach is safer for multiple Node workers on one host. SQLite itself is not a multi-host coordination solution.

OpenAI-specific responsibilities
Current official OpenAI guidance additionally describes:

Keep these in configuration or an OpenAI integration adapter. Do not make all MCP clients present an OpenAI client certificate, and do not branch Spotify tool behavior based on “ChatGPT” versus “Qwen.”
Disconnect and revocation are separate actions
Define three distinct operations:
Revoke an MCP client authorization: the client can no longer call Baikai, but the Spotify link may remain.
Disconnect Spotify: delete or tombstone the Spotify connection; MCP identity remains and tools report that Spotify must be reconnected.
Delete the Baikai account: revoke MCP credentials and remove the Spotify connection.
Do not initially expose account deletion or disconnect as autonomous model tools. Provide a user-controlled web/account flow.

11. Risks and unknowns
Deployment model is unknown. SQLite and the current filesystem playback lock assume durable storage on one host. Multi-host deployment would require a different shared datastore and lock strategy.

Production Node version is unknown. The inspected local version is Node 22.21.1, but package.json has no engines field.

MCP client protocol support will vary. The current MCP SDK/spec is newer than many deployed clients. The coach must test whether compatibility mode is needed.

Authorization-server strategy is undecided. External IdP versus embedded OAuth materially changes Milestone 6’s code and schema.

Baikai identity semantics are undecided. Determine whether one internal user always means one Spotify account, and whether the same Spotify account may be linked through multiple MCP identities.

No user-facing account management exists. Reconnect, disconnect, consent, and deletion require web UX or carefully scoped routes.

Taste-profile behavior is untested. Existing output/schema mismatches and a sampling-shape inconsistency must be characterized before extraction.

Most non-playback controllers lack tests. Service extraction needs new contract tests to avoid accidental REST changes.

The OpenAPI document has drift. Some actual routes are absent; several response schemas do not exactly match controller envelopes. Do not let MCP inherit these inaccuracies.

Legacy OAuth has security limitations. It returns Spotify tokens, lacks Baikai identity, and the regular login path lacks state validation. Preserve it for compatibility, but do not copy its architecture.

Refresh concurrency needs an explicit policy. In-memory single-flight alone would not cover multiple Node workers.

Spotify authorization can require re-consent. The current scope string contains a duplicate and should become a documented canonical set. Current Spotify scopes should be verified when tools are added. Spotify scopes.

Playback storage remains separate. SQLite does not automatically replace .spotify-playback/. Migrating the buffer playlist ID into SQLite could be considered later, but is unnecessary for the initial MCP migration and risks destabilizing proven behavior.

The worktree is not clean. controllers/authController.test.js was untracked before inspection; do not overwrite or discard it. The test directories are also ignored in .gitignore, despite an existing tracked playback test.
